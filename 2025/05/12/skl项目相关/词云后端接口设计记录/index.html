以下是词云接口设计的记录。

1.在数据库层建立索引

全文索引提供了更灵活的服务，比如：

　　1. like 只是进行模式匹配，全文索引却提供了一些语法语义的查询功能，会将要查的字符串进行分词操作，这决定于MySQL的词库。

　　2. 全文索引可以自己设置词语的最小、最大长度，要忽略的词，这些都是可以设置的。

　　3. 用全文索引去某个列查一个字符串，会返回匹配度，可以理解为匹配的关键字个数，是个浮点数。

总之就是，全文索引因为用上了索引，性能更高，有词库支撑可以进行分词提供了一些语义查询的功能，有词语停用表忽略某些词语，有词语最大最小值可以设置等更灵活。

参考链接：https://www.cnblogs.com/qsws/p/11883442.html

2.GET请求接口设计

这个接口主要是返回cssci_info论文表中，每个关键词出现的次数。之后获取topN个关键词的POST请求接口在这个接口的基础上实现。

（1）存在的问题

由于论文表的数据量非常大，因此，在数据访问层（infrastructure）需要定义合理的Mapper以及在数据库（mysql）层设计合理的查询语句，以提升查询的性能，减少数据请求后返回数据的时长。

（2）创建存储过程（统计关键词）

（利用 JSON_TABLE 来拆分关键词并进行统计。对于大型数据集（cssci_info表有80万行），这种方法通常比逐行基于游标的拆分或递归 CTE 具有显著的性能优势。）

这个存储过程将执行以下操作：

  1. 接收以分号分隔的 keywords 字符串。

  2. 移除任何开头或结尾的分号，以避免在两端产生空的关键词。

  3. 将其转换为 JSON 数组字符串（例如，"kw1;kw2;kw3" 变为 ["kw1","kw2","kw3"]）。

  4. 使用 JSON_TABLE 将此 JSON 数组展开为多行。

  5. 按提取的关键词分组并统计数量。

（3）定义Mapper

这种方法的优点：

  1. 性能: JSON_TABLE 是在 MySQL 内部用 C/C++ 实现的，针对 JSON 处理和此类“将字符串拆分为行”的操作进行了高度优化。对于大型表，它通常比手动字符串操作（如循环或递归 CTE）快得多。
  2. 动态关键词数量: 它可以处理 keywords 字符串中任意数量的关键词，而无需像之前那样指定一个上限（例如10个）。
  3. Mapper 中 SQL 更简洁: Java 代码现在只有一个对存储过程的简单调用，将复杂的 SQL 逻辑封装在了数据库内部。
  4. 更好地处理边缘情况: TRIM(BOTH ';') 和后续的 WHERE TRIM(jt.keyword_val) != '' 有助于更稳健地管理格式不正确的关键词字符串（如开头/结尾有分号，或连续多个分号）。
